    Configuration validation and generated-input pilot

    Issue: #322. Baseline: 9e79bac6371e1fa498dd4fb23715863026c3d091 (current main at investigation).

    Baseline and decision¶

    On 2026-11-06 the public assessment JSON reported Passing 100%, Silver 45%, Gold 13%. An unanswered criterion does not demonstrate an absent control. Existing architecture documentation, Pester CI and the scanner threat model already supply evidence not reflected in some answers. This investigation does not attest to maintainer training, governance, access continuity, review percentages, or repository-wide coverage.

    Current source and policy, rather than historical implementation tasks in the multi-targeting plan, establish three runtime bundles: PowerShell 7.4.21/.NET 8.0.32/net8.0, 7.5.12/9.0.21/net9.0 and 7.6.7/10.0.13/net10.0. The shipped profile policy checks PowerShell and CLR identity; the CI matrix covers Windows, Linux and macOS x64. The SDK is pinned to 10.0.302; Pester to 5.7.1. Existing locked dependencies, profile-aware dependency policy, package-composition checks, lifecycle checks and authenticated release-evidence gates remain unchanged. Release jobs bind tagging, build and publishing to an immutable source revision. No release was performed.

    Configuration validation wins because there is a directly reproducible behavior gap in project-owned code and inexpensive, independent contract assertions. {"ShowLogo":"false"} previously becomes true; [{"ShowLogo":false}] is accepted as an object. These are minimized regressions from contract inspection, not vulnerabilities discovered by coverage-guided fuzzing. No privilege escalation is claimed: the configuration is controlled by the user running the module. Review also identified automatic date-string conversion in PowerShell’s JSON parser. The implementation uses the supported runtimes’ built-in System.Text.Json document API to validate JSON kinds and retain exact strings without adding a dependency. The document is disposed even when validation fails.

    Contract and testing strategy¶

    Only an object root is accepted. Non-null booleans must be JSON booleans; a non-null skip list must be an array of strings. Missing/null settings retain defaults and unknown keys remain ignored for compatibility. String contents are literal filename comparisons in Import-DPLibrary, not executable code, wildcard patterns or paths to load. The entire invalid configuration is discarded through the existing DPConfigReadFailed/defaults behavior; ErrorAction Stop terminates. Set-DPConfig’s existing write behavior is outside this change; hand-edited invalid values must not be relied upon to survive its existing normalization either. Recognized setting names remain case-insensitive; duplicates are now rejected instead of allowing ambiguous preferences. Comments and trailing commas remain accepted. The document parser limits nesting to 64 levels, including unknown settings; there is no new file-size bound.

    The pilot uses Pester’s TestDrive and redirects file reads to one fixture. It never reads or writes the real configuration, imports installed service modules, loads generated assemblies, or uses credentials/tenants. Production JSON parsing and validation are not mocked. The existing missing-file and read-error tests remain. Independent properties are preservation of known typed values (including order, case and duplicates), complete default fallback and one stable error on a deliberately invalid type, and terminating-error semantics. The oracle does not reimplement normalization.

    Default seeds: 11450, 322, 20261106, 32 cases per seed, each testing a valid object and one wrong-type mutation (192 generated inputs). Inputs contain at most eight short names and bounded nesting. Explicit fixtures cover roots, scalar lists, nested/mixed lists, null members, syntax errors and missing/null fields. Each seed has a 60-second elapsed-budget assertion; run the process with an outer 180-second timeout to interrupt a stuck call. Diagnostics include seed, case and complete synthetic JSON. Keep any newly discovered defect as a small explicit fixture before changing the generator. Fixed seeds are a reproducible pilot, not exhaustive exploration; .NET Random streams may differ across runtimes, so record the runtime and emitted failing JSON as well as the seed.

    Replay¶

    Use the exact executable provisioned by tools/Install-DLLPickleTestPowerShell.ps1 from build/powershell-test-matrix.json, and Pester from build/build-tool-versions.json. First provision the selected runtime and pinned tools while networking is allowed. For example, save the provisioner’s returned executable path:

    $Matrix = Get-Content ./build/powershell-test-matrix.json -Raw | ConvertFrom-Json
$Provision = @{
    Provider = 'DirectArchive'
    PowerShellVersion = $Matrix.profiles[0].powerShellVersion
}
$Executable = ./tools/Install-DLLPickleTestPowerShell.ps1 @Provision

    After disabling networking, invoke the helper in a fresh process (from the repository root). The argument array also makes the process timeout explicit:

    $ReplayArguments = @(
    '-NoProfile', '-NonInteractive', '-File'
    './build/Invoke-DLLPicklePester.ps1'
    '-TestPath', './tests/Unit/Get-DPConfig.Property.Tests.ps1'
    '-SummaryPath', './summary.json'
    '-TestResultPath', './results.xml'
    '-RequiredPesterVersion', '5.7.1'
)
# Linux: external timeout interrupts a stuck call.
timeout 180 $Executable @ReplayArguments
if ($LASTEXITCODE -ne 0 -or
    (Get-Content ./summary.json -Raw | ConvertFrom-Json).FailedCount -ne 0) {
    throw 'Configuration pilot failed; inspect results.xml.'
}
# Other hosts: launch with & $Executable @ReplayArguments and enforce
# a 180-second timeout in the parent process supervisor.

    To replay one seed, run this in a fresh process using the same executable (and the same external process timeout):

    & $Executable -NoProfile -NonInteractive -Command {
    Import-Module Pester -RequiredVersion 5.7.1
    $Container = New-PesterContainer -Path (
        './tests/Unit/Get-DPConfig.Property.Tests.ps1'
    ) -Data @{ Seeds = @(322); CasesPerSeed = 32 }
    $Result = Invoke-Pester -Container $Container -Output Detailed -PassThru
    if ($Result.FailedCount -gt 0) { exit 1 }
}

    Do not use execution timeouts as an assertion that large arbitrary configuration files are resource-bounded: this patch sets no production file-size limit.

    Fuzzing and assessment boundaries¶

    These are seeded generated-input/property tests, not coverage-guided fuzzing. SharpFuzz instruments .NET assemblies and supports AFL/libFuzzer; the selected behavior is PowerShell script, while JSON parsing is provided by PowerShell. Instrumenting the engine would primarily test dependencies and require a substantially different harness. The dependency bundle project is not a project-owned parser target. No concrete supported target here justifies OSS-Fuzz enrollment or an architectural rewrite. The OSS-Fuzz guide requires integrated fuzz targets and a build/runner environment.

    Scorecard Fuzzing detects OSS-Fuzz, ClusterFuzzLite and specified language/library integrations; Pester is not among them. Best Practices has different criteria: its Silver criteria require all relevant untrusted inputs to be validated, and its dynamic_analysis_unsafe concerns memory-unsafe project code with memory-safety detection. This pilot provides neither whole-project validation nor memory-safety instrumentation. No Gold criterion becomes satisfied from this patch.

    Scanner environment PR #319 is separate from enrollment PR #1417, which was still open/unmerged when rechecked on 2026-11-06. Local offline tests are not evidence of active Anthropic scanning.
